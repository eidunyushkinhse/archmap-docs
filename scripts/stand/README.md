# Стенд для скриншотов документации

Скриншоты снимаются с локального ArchMap на ОТДЕЛЬНОЙ чистой базе `archmap_docs`: в ней
только две учётки (`architect`, `reader`, пароль — `DOCS_STAND_PASSWORD`, по умолчанию
`docs-stand-2026`) и три проекта из архивов знания: «Маркетплейс «Ярмарка»», «Zabbix 7»,
«Grafana». Рабочие проекты владельца в кадр не попадают (репозиторий публичный).

1. Экспортировать архивы эталонов из рабочей базы (GET /api/v1/export/archive с
   X-Project-Id) в папку, например `~/archmap-docs-archives/`: `yarmarka.zip`, `zabbix.zip`,
   `grafana.zip`.
2. Поднять стек соседнего репозитория archmap на базе стенда. ВАЖНО: одного `DB_NAME` мало —
   бэкенд читает `DATABASE_URL` из `backend/.env`, поэтому его надо переопределить явно:
   ```bash
   DB_NAME=archmap_docs DATABASE_URL=postgresql://postgres:postgres@localhost:5432/archmap_docs ./dev.sh
   ```
3. Один раз посеять: `bash scripts/stand/seed.sh ~/archmap-docs-archives`.
4. Снимать: `node scripts/stand/shots.mjs projects` (экран «Проекты»),
   `node scripts/stand/shots.mjs home "Маркетплейс «Ярмарка»"` (страница проекта).
   Файлы ложатся в `content/images/` (или `OUT=…`). Окно 1440×900, масштаб 2, учётка
   `reader` (другая — `DOCS_USER`/`DOCS_PASS`).

Корневой уровень «Ярмарки» на стенде расставлен руками (PUT /views/root/layout): авто-раскладка
кладёт шесть объектов в столбик, и на странице проекта они нечитаемы.

## Пересъёмка всех снимков

Все снимки сайта переснимает `scripts/stand/all.sh`: по строке на снимок в порядке страниц
руководств, в каждой строке учётка (`DOCS_USER`), режим `shots.mjs`, его аргументы и переменные
кадра (`CLIP_H`, `SIDE`). Адреса стенда берутся из окружения:

```bash
FRONTEND=http://localhost:5176 BACKEND=http://localhost:8003 bash scripts/stand/all.sh
```

Без `FRONTEND` и `BACKEND` скрипт смотрит на стенд по умолчанию (:5173 и :8000). Прогон всех
38 снимков занимает около трёх минут; один браузер за раз, кадры идут друг за другом.
`all.sh` останавливается на первом кадре, который не снялся.

Один кадр или несколько: имена файлов аргументами, остальные строки пропускаются:

```bash
FRONTEND=… BACKEND=… bash scripts/stand/all.sh tree-search.png legend-types.png
```

Можно и скопировать строку из `all.sh` и запустить её из `scripts/stand/` (там `"$P"` — имя
проекта «Маркетплейс «Ярмарка»»). После пересъёмки каждый кадр нужно открыть и посмотреть: в
кадре не должно быть состояния загрузки, тостов, ошибок и обрезанных окон.

## Данные стенда

Кадры рассчитаны на такие данные (всё, кроме версий и раскладок, приходит из архивов посева):

- учётки `architect` (общая роль «Архитектор», владелец трёх проектов) и `reader`
  («Пользователь», читатель во всех трёх);
- «Маркетплейс «Ярмарка»» из архива эталона: система «Заказы» с контейнером «Оркестратор
  заказа» (компоненты «Приём событий» и «Шаги саги»), Order API с источником
  `github.com/yarmarka/orders / services/order-api`, схемами логики и конфигурацией, БД заказов
  со структурой, Kafka с каналами, «Сервис уведомлений» с выводимым SMS-рассыльщиком, процессы
  «Оплата заказа» и «Оформление заказа», площадки «Облако» (кластеры prod и резерв, Managed
  PostgreSQL, ВМ брокера и поиска) и «Серверная офиса» с размещением объектов;
- «Zabbix 7»: у системы «Zabbix» в разделе «Связи» строки с «×2» (кадр `object-edges.png`);
- у системы «Заказы» две версии документации: v1 «Релиз 2026.10 · ORD-430» и v2 «Релиз
  2026.11 · ORD-512: таймаут оплаты» (`POST /api/v1/nodes/<id>/versions` с телом
  `{"comment": "…"}` учёткой `architect`). Между v1 и v2 правлены описание Order API, схема
  «Создание заказа» и конфигурация «Оркестратора заказа»; текущая документация с v2 расходится,
  поэтому у архитектора над списком версий строка «Есть изменения с v2»;
- корневой уровень «Ярмарки» расставлен руками (см. выше), холст «Развёртывание» открывался
  до съёмки (первый показ вида пишет его раскладку);
- статус страницы у всех объектов «В работе»; токенов у `architect` и `reader` нет;
  напоминаний о слиянии в «Ярмарке» нет (`GET /api/v1/nodes/alerts`, поле `code_changes`).

Данные на время кадра режимы готовят и убирают сами:

- `status` ставит названным объектам статус «Согласовано» (`PATCH /api/v1/nodes/<id>` с
  `{"approval": "approved"}`) и после кадра возвращает «В работе»;
- `tokens` отзывает все токены учётки, выпускает токен «Ноутбук» для списка и после кадра
  снова отзывает все токены; `ci-token` отзывает только выпущенный в кадре токен;
- `code-change` выпускает токен «Только сигнал из CI» (`POST /api/v1/tokens` с
  `{"name": "CI съёмки", "ci_only": true}`), трижды шлёт им `POST /api/v1/code-changes` с телом
  `{"repo": "https://github.com/yarmarka/orders", "commit": "<40 hex>", "branch": "main"}`, а после
  кадра снимает напоминание (`DELETE /api/v1/code-changes/<id>` с `X-Project-Id`) и отзывает
  токен.

Остальные режимы ничего не сохраняют: окна закрываются без создания, «Восстановить версию» не
подтверждается, режим размещения отменяется.

## Английские скриншоты

Продукт пока не переведён, поэтому для `content/en/images/` снимается «прототип» тех же окон:
`DOCS_LANG=en node scripts/stand/shots.mjs …` с теми же аргументами (имена из данных — по-русски,
как в базе стенда). Тексты подменяются по двум словарям ru→en (`en.mjs`):

- `en/ui.json` — подписи интерфейса. Это и глоссарий английской документации: элемент
  интерфейса в тексте страницы называется так же, как в словаре;
- `en/data.json` — данные демо-проектов: имена объектов, описания, подписи связей, процессы,
  схемы логики, структура БД, каналы, конфигурация.

Данные переводятся в ответах API до отрисовки, поэтому схемы раскладываются по английским
подписям. Подписи интерфейса подменяются на странице перед кадром. Если на экране осталась
кириллица, скрипт печатает остатки, а `MISS_OUT=<файл>` дописывает в файл все ненайденные куски
текста — их переводят в словаре и снимают кадр заново. Поиск по дереву идёт на бэкенде по
русским именам: английский запрос дополняется русской формой (таблица `SEARCH` в `en.mjs`).
